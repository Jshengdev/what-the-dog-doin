# GOAL: the body (Unitree Go2)

**Goal.** One Python process that holds a single WebRTC connection to the dog and exposes: state (mode, odometry position, velocity, IMU, obstacle range) as a stream, the predefined sport commands (Sit, RiseSit, StandUp, StandDown, Hello, Stretch, Move x/y/z for a duration, StopMove, Dance1), a scripted route runner (a list of moves with durations, obstacle avoidance on), and the latest camera frame as a JPEG on demand. Every command writes a ledger row with the state read back after it.

**Loop.** Build `wtdd/dog/__main__.py` so `python -m wtdd.dog <cmd>` works, run `probe`, fix, repeat. Without a dog on the network you can only verify imports, CLI help, discovery scan, and the code path by reading the driver source; say exactly that in the report.

**Commands.** `probe` (discovery via multicast `discover_ip_sn`, env check, key check; prints what is blocked) · `state` (print one LF_SPORT_MOD_STATE message and the measured publish rate over 3 s) · `cmd <Name>` (any SPORT_CMD by name; switches motion mode to normal first) · `move --x 0.3 --seconds 3` · `route <file.json>` (list of steps; each step = a sport command or a move; obstacle avoidance toggled on; state row after each) · `frame --out ~/Pictures/wtdd/frame.jpg` (camera track, JPEG, sha256 in the ledger; see `docs/VISION.md` §1) · `commands` (print the 49 predefined SPORT_CMD names with ids).

**Done when.** `commands` lists the predefined set; `probe` reports a reachable dog (once one exists) or the precise missing pieces; `state` prints a live row; `cmd Sit` then `cmd RiseSit` produce ledger rows whose state_after mode changed; `frame` writes a JPEG; `route` runs a three-step corridor route.

**Facts (verified from the driver source).** Package `unitree_webrtc_connect` (installed in `.venv`). `UnitreeWebRTCConnection(WebRTCConnectionMethod.LocalSTA, ip=..., aes_128_key=...)`; `await conn.connect()`; requests via `conn.datachannel.pub_sub.publish_request_new(RTC_TOPIC["SPORT_MOD"], {"api_id": SPORT_CMD["Hello"]})`; motion mode via `RTC_TOPIC["MOTION_SWITCHER"]` api 1001 (query) / 1002 (set "normal"); state via `conn.datachannel.pub_sub.subscribe(RTC_TOPIC["LF_SPORT_MOD_STATE"], cb)`; obstacle avoidance via `RTC_TOPIC["OBSTACLES_AVOID"]` with `OBSTACLES_AVOID_API`, joystick-style drive via `publish_without_callback(RTC_TOPIC["WIRELESS_CONTROLLER"], {"lx","ly","rx","ry","keys"})` at 50 Hz; camera via `conn.video.add_track_callback(cb)` then `conn.video.switchVideoChannel(True)`. Firmware 1.1.15+ needs `aes_128_key` fetched once with `unitree-fetch-aes-key`. Path finding: the driver names LiDAR mapping and navigation topics but implements no example for them; there is no waypoint navigation in 6.5 hours. The route is a scripted list of moves with obstacle avoidance on; `TrajectoryFollow` (1018) exists for short trajectories if needed.

**Johnny must do (prompt him).** 1) Put the dog on the house Wi-Fi in STA mode via the Unitree Go app and note its IP. 2) Read the firmware version in the app; if 1.1.15 or newer, run `unitree-fetch-aes-key --email <unitree account> --password '...' --device-type Go2` and put the key in .env. 3) Clear a 3 m corridor and stand by the dog for the first `cmd` calls.

**Never.** No commands to the dog unless `probe` succeeded in this process; no flips, no jumps; no silent reconnect loops; no git commit.
